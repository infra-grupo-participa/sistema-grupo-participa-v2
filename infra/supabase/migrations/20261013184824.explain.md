# 20261013184824: listas da Black davam 21000 pela API (safeupdate)

**Situação: APLICADA em 13/10/2026 às 18:48:24 UTC.** Foi escrita como `20261013184806`; o número antigo ficou só dentro dos
corpos das funções.

## Por que

Depois do deploy da Fase 1 (merge `1474db8`), a aba Mensageria mostrava "Não foi possível ler a lista agora".

- Pela API, `dados_black_listas_resumo` e `dados_black_lista` respondiam `400 {"code":"21000","message":"UPDATE requires a
  WHERE clause"}`.
- O Supabase carrega a extensão **safeupdate** nas sessões do PostgREST, e ela recusa UPDATE sem WHERE, mesmo numa tabela
  temporária.
- `dados.black_base_pessoas` e `dados.black_lista_disparo_montar` tinham `update <temp> set dig = ...` e
  `update <temp> set comp = id` sem WHERE.
- Os ensaios rodam pela Management API, que não carrega a safeupdate (`LOAD 'safeupdate'` dá 42501 ali), por isso
  passaram.

## O que muda

Só `where true` nesses 2 UPDATEs de cada função. As regras e as contagens não mudam.

## Prova

- **Ensaio:** base e planilha com 650 / 650 antes, depois e revertida.
- **API com sessão de usuário** (conta sintética QA Sessões, master): o resumo responde 200, e a lista também.
- **E2E em produção:** os 3 CSVs baixam, as linhas batem com os botões e o log grava.

## Lição

RPC chamada pela API precisa ser provada também por uma chamada REST de verdade, não só pelo ensaio da Management API.
