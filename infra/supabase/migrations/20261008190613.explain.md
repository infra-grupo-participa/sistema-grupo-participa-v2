## O que muda

| Peça | Detalhe |
|---|---|
| `crm.conversa` / `crm.mensagem` | colunas `excluida_em`, `excluida_por`, `excluida_motivo` (5-300 caracteres) + CHECK de coerência. Exclusão **lógica**: nenhuma linha é apagada. |
| unicidade | `conversa_numero_id_telefone_key` (unique) → índice único parcial `conversa_numero_telefone_viva_key (numero_id, telefone) where excluida_em is null`. A excluída fica no histórico e não trava a conversa nova. Os 3 `on conflict (numero_id, telefone)` vivos ganharam `where excluida_em is null` (senão o Postgres não infere o índice parcial). |
| RLS | `conversa_ler` e `mensagem_ler` recriadas com `excluida_em is null and (regra de antes)`. |
| `crm.log` | `log_entidade_check` aceita `'conversa'` (lido vivo antes de reescrever; 15.795 linhas validadas). |
| `public.crm_excluir_conversa(p_conversa uuid, p_motivo text)` | SECURITY DEFINER, `search_path = ''`. `crm.guarda_escrita()` (leitor, escrita desligada, fora do Comercial) → gestor (`crm.eh_gestor(uid)`) → motivo 5-300 → `for update` na conversa → marca mensagens e conversa (zera não lidas) → `crm.log_registrar('excluiu','conversa', id, pessoa=null, resumo com nº de mensagens e motivo, dados {mensagens, motivo, canal_id, midias})` → `realtime.send({t:'conversa'}, 'mudou', 'crm:caixa')`. Mensagem `na_fila` vira `falhou` ("Conversa excluída antes do envio.") e mídia `pendente` vira `falhou`: nada mais sai nem é baixado. Devolve `{ok, msg, mensagens, midias[]}`. `revoke` de public/anon; `grant` a authenticated e service_role. |
| entradas (2ª migration) | `crm.whatsapp_entrada` e `crm.evolution_entrada`: sem conversa viva para número + telefone e com uma excluída, a nova nasce no **mesmo contato** da excluída (sem `pessoas.registrar`). Sem isso, o casamento por telefone caiu em outra pessoa no ensaio. |

## Mídia (bucket privado `crm-midia`)

A RPC devolve os caminhos que só as mensagens da conversa usam (`midia_caminho` já é único em `crm.mensagem`). O Route
Handler `POST /api/comercial/conversas/excluir` chama a RPC com o JWT de quem clicou e, **só depois do ok**, apaga esses
arquivos com service role (caminhos vindos do banco, validados pelo mesmo padrão do CHECK). Falhou o storage: a exclusão
vale e a tela avisa "N arquivo(s) ficaram para limpeza posterior". Limpeza posterior (listar e apagar pela API de Storage):

```sql
select m.midia_caminho from crm.mensagem m
  join storage.objects o on o.bucket_id = 'crm-midia' and o.name = m.midia_caminho
 where m.excluida_em is not null;
```

## As 5 perguntas

- **Escala:** a exclusão toca só as mensagens de uma conversa (índice `mensagem_conversa_idx`); o filtro nas leituras é
  um predicado sobre linhas já lidas.
- **Índice:** o planner usa os mesmos índices de antes (acima).
- **Frequência:** clique manual do gestor, raro.
- **Repetição:** um aviso realtime por exclusão; as telas abertas recarregam uma vez.
- **Reversão:** abaixo.

## Reversão

- Desligar o botão: `revoke execute on function public.crm_excluir_conversa(uuid, text) from authenticated`.
- Desfazer uma exclusão (antes de chegar mensagem nova no mesmo número/telefone, por causa do índice único parcial):
  `update crm.mensagem set excluida_em = null, excluida_por = null, excluida_motivo = null where conversa_id = '<id>';`
  `update crm.conversa set excluida_em = null, excluida_por = null, excluida_motivo = null where id = '<id>';`
  (as mídias apagadas do storage não voltam).
- Corpos antigos: md5 vivos antes estão na premissa da migration (`pg_get_functiondef` de 08/10/2026).
