## 2. O que a migration cria

- `crm.mcp_token` (hash sha-256 hex único, escopos ⊂ {ler, operar} com `ler` obrigatório, validade ≤ 180 dias,
  revogação por carimbo) e `crm.mcp_chamada` (auditoria + limite). RLS ligada, sem policy, sem grant.
- `crm.mcp_papel(uuid)` (régua de `eh_gestor`/`eh_vendedor` para um perfil qualquer; sem grant).
- `public.crm_mcp_criar_token`, `crm_mcp_tokens`, `crm_mcp_revogar_token` → authenticated (guarda `eh_comercial`;
  o próprio; gestor lista/revoga todos; revogar funciona com `mcp_ligado=false`).
- `public.crm_mcp_autenticar(p_hash, p_ferramenta)` → **só service_role**.
- `public.crm_funil_resumo(p_funil)` e `public.crm_desempenho(p_desde, p_ate)` → authenticated, `SECURITY INVOKER` + RLS.
- `crm.tg_log` recriado a partir do corpo VIVO (md5 `450774b2…` conferido na guarda) com 1 linha a mais.

Planos (2ª rodada):
- resumo, abertos por etapa: `Nested Loop → Index Scan using negocio_funil_aberto_idx (funil_id, etapa_id)`, 1,4–1,8 ms.
  O resto dos ~38 ms são os 3 subtotais de 30 dias do funil (ganhos/valor/perdidos) sobre a massa toda fechada no mês —
  pior caso deliberado.

- limite: `Index Only Scan using mcp_chamada_token_idx`, Heap Fetches 8. Token: `Index Scan using mcp_token_hash_sha256_key`.
