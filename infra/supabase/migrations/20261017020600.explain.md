## 1. O que e por quê
A integração grava e-mail (ActiveCampaign) e WhatsApp API (Unichat) com `projeto_id` nulo quando o nome da campanha não traz `[SIGLA]`. O banco só aceita projeto nulo em `origem = 'api'` (`disparos_projeto_fora_da_api`). Estes 7 são da Clínica pelo nome e entram no dashboard dela só com o projeto ligado. ## 2. Decisões
- **Ferramenta do WhatsApp API é o Unichat (id 2), não o Infobip.** O pedido dizia Infobip; os dois disparos estão gravados com `origem_sistema = 'unichat'`. Nada foi mudado na ferramenta.
- **Ficaram de fora** (nome com "clinica", mas fora do pedido, pós-compra): `[CLINICA-INT] Compra Aprovada - v2` (id 50162, email) e `clinica_compraaprovada_v2` (id 50132, unichat), ambos com 13 contatos em 15/10. Ligar é um `update` de uma linha cada, se o Victor quiser.
- **Ficaram de fora** os grupos `ALUNOS ATIVOS` do SendFlow (nome reaproveitado por outros eventos; entram pela planilha, que diz a data e a mensagem).
- **Custo não foi tocado.** Sem custo, `custo_completo = false` no WhatsApp (e-mail do ActiveCampaign não tem custo em lugar nenhum). Mesma situação que levou à `20261014140100` no ATM.
- Sem `set_config('mkt_mensageria.autor_api')`: o check `historico_por_api_check` só aceita `api:[a-z_]{2,40}`, e a precedente (`20261014140000`) também não define. O histórico registra as 7 alterações com `por_api` nulo.

## 3. Quem lê (grep antes de alterar)
`projeto_id` destes 7 era nulo: só aparecia na lista de pendência `sem_projeto` do módulo Mensageria (`web/modules/marketing/mensageria`), onde eles saem (efeito pretendido). Nenhuma função de outro dashboard (ATM, Black) os lê: todas filtram `projeto_id` do próprio projeto. `dados_presencial_resumo` (Clínica) passa a contar 7 disparos: ver Risco abaixo.

## 4. As 5 perguntas
7 linhas; índice = PK; uma vez; idempotente (`where projeto_id is null and origem = 'api'`, com trava que confere os 7 antes); reversão `20261017020600_reversao.sql` (volta a nulo; nada é apagado).

## 5. ATENÇÃO para quando a planilha da Clínica for ativada
A aba API da planilha tem exatamente as mensagens 39925 e 40560. O sync cria linha **nova** (origem `planilha`); a "adoção" só casa disparo de origem `manual` ou `planilha`, não `api`. Sem desligar o vínculo, essas 2 mensagens contariam duas vezes. Na migration que ativar a planilha: `update mkt_mensageria.disparos set projeto_id = null where id in (39925, 40560) and projeto_id = 68 and origem = 'api';` (SQL pronto em `docs/dashboard-presencial.md` §2.13.3).

## 6. Risco conhecido (fora do escopo, não alterado)
`public.dados_presencial_resumo` calcula `custo_completo` com todos os disparos do projeto, inclusive e-mail (sem custo). Com e-mail ligado, `custo_completo` fica falso mesmo com todo o canal pago com custo, e CAC / custo por pré-checkout seguem nulos. Hoje já eram nulos (0 disparos). A `dados_atm_resumo` usa só canal pago; alinhar a da Clínica é uma migration à parte, a pedir ao Victor.
