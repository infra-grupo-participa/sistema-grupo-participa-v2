- `public.handle_new_user()` (gatilho `on_auth_user_created`, AFTER INSERT em `auth.users`): gravava
  `perfis.cargo` e `perfis.status` a partir de `raw_user_meta_data` (escrito por quem se cadastra).
- `public.gp_eh_equipe()`: ativo e e-mail `@advmais.com`. `public.gp_is_admin()`: ativo e cargo dev/admin, **sem

- `public.perfis`: RLS ligada; policies `todos_auth_podem_ler` (SELECT, authenticated, `true`),
  `usuario_atualiza_proprio` (UPDATE), e duas RESTRICTIVE (`gps_block_aluno`, `sip_cannot_access_perfis`). GRANT de
  tabela para `anon` e `authenticated`: SELECT, INSERT, DELETE, REFERENCES, TRIGGER; UPDATE de coluna só
  `nome`, `avatar_url`, `atualizado_em` para authenticated. `disparos_ui_ro` (BYPASSRLS) tem SELECT.
- Outros 6 gatilhos em `auth.users` (central, gps, metodo, rede, workbook x2): o `auth.users` é de ~7 sistemas.

## Quem entra de verdade (para não travar)

- **v2:** convite do admin. `web/app/api/admin/usuarios/route.ts` POST faz `generateLink({type:'invite'})` **sem
  metadata** e logo depois, com service_role, grava `status = 'ativo'`, cargo, áreas e funções. Não depende do metadata.
  Login por senha (`web/app/login/page.tsx`), recuperação por `resetPasswordForEmail`, `/auth/confirm` com `verifyOtp`.
  Não há `signUp` no v2.
- **Outros sistemas usam o cadastro público** (metadata com `sub`/`email_verified`, que o GoTrue grava no signup):
  milhares de contas de jul a out/2026, a mais recente em 06/10/2026 (chaves `sistema`, `origem`, `documento`). Por isso
  **o Auth não foi mexido**: `disable_signup = true` ou `mailer_autoconfirm = false` quebraria esses cadastros.
- 9 contas de equipe foram criadas por API de admin com metadata `{cargo, status}` (mar a set/2026, origem não achada
  nos repositórios clonados). Depois desta migration, conta criada assim nasce pendente e precisa ser ativada na tela
  Usuários.

## O que muda

1. `handle_new_user`: mesmo corpo vigente; o INSERT passa a gravar `'visualizador'` e `'pendente'` fixos. Quem recebe
   perfil continua igual.
2. `gp_is_admin`: mesmo corpo + `AND p.email ILIKE '%@advmais.com'`. Mesma assinatura, ACL preservado (1 sobrecarga).
3. `perfis`: `revoke all ... from anon`; `revoke insert, delete, truncate, references, trigger ... from authenticated`.

Guarda de premissa aborta se: faltar alguma das 3 funções; o gatilho não estiver ligado a `handle_new_user`; houver
perfil ativo dev/admin fora de `@advmais.com`. **A guarda se provou na 1ª rodada:** o cadastro forjado de fora do
domínio do t0 (ativo/admin) fez a migration abortar; o ensaio passou a apagar os cadastros do t0 antes da passada 1.

## Fora daqui, de propósito

- Policy `todos_auth_podem_ler`: `pg_stat_statements` mostra authenticated lendo perfis de terceiros por id
  (~36 mil chamadas `id, nome, email, cargo, status where id = $1`; ~2 mil `nome where id = $1`; ~500 `id = any`), sem
  origem identificada nos repositórios clonados. Restringir sem saber quem chama pode quebrar outro sistema.
- EXECUTE de `handle_new_user` (PUBLIC tem): função de gatilho não é chamável por RPC; mexer no ACL não fecha nada.
- Contas existentes (QA, perfis duplicados): decisão do Victor.

## Explain (2ª execução de cada, cache quente)

- `select public.gp_is_admin()` com JWT de um admin real: antes 0,225 a 0,363 ms, depois 0,225 a 0,239 ms,
  `Buffers: shared hit=3` nos dois (busca por PK; o `ilike` é sobre 1 linha).
- Cadastro (`insert into auth.users` com os 7 gatilhos): `on_auth_user_created` 0,37 ms antes, 0,20 a 0,27 ms depois;
  execução total 1,2 a 7,0 ms, dominada pelos gatilhos `rede` e `reivindica_pesquisa` (de outros sistemas).

## As 5 perguntas

- **Escala:** `gp_is_admin` lê 1 linha por PK; o gatilho grava 1 linha por cadastro. Não muda com 10x.
- **Índice:** PK de `perfis` (`Buffers: shared hit=3`).
- **Frequência:** `gp_is_admin` por chamada de policy/RPC (igual a hoje); gatilho por cadastro.
- **Repetição:** nenhuma consulta nova.
- **Reversão:** corpos anteriores abaixo + `grant all on public.perfis to anon; grant insert, delete, truncate,
  references, trigger on public.perfis to authenticated;`. Nenhuma linha de dado é alterada.

## Corpos anteriores (pg_get_functiondef, 07/10/2026), para reverter

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
 RETURNS trigger
 LANGUAGE plpgsql
 SECURITY DEFINER
 SET search_path TO 'public'
AS $function$
declare
  v_portal text := coalesce(new.raw_user_meta_data->>'origem', new.raw_user_meta_data->>'sistema', '');
  v_declara_equipe boolean := (new.raw_user_meta_data ? 'cargo') or (new.raw_user_meta_data ? 'status');
  v_email_equipe boolean := coalesce(new.email, '') ilike '%@advmais.com';
BEGIN
  IF NEW.raw_app_meta_data->>'role' IN ('admin', 'mentor', 'student') THEN
    RETURN NEW;
  END IF;

  -- Cadastro veio de um portal de aluno: não é equipe.
  IF v_portal <> '' AND NOT v_declara_equipe THEN
    RETURN NEW;
  END IF;

  -- Sem sinal de equipe (nem cargo/status, nem e-mail do domínio): não é equipe.
  IF NOT v_declara_equipe AND NOT v_email_equipe THEN
    RETURN NEW;
  END IF;

  INSERT INTO public.perfis (id, nome, email, cargo, status)
  VALUES (NEW.id,
    COALESCE(NEW.raw_user_meta_data->>'nome', split_part(NEW.email, '@', 1)),
    NEW.email,
    CASE WHEN NEW.raw_user_meta_data->>'cargo' IN ('dev','admin','gestor','operador','visualizador')
         THEN NEW.raw_user_meta_data->>'cargo' ELSE 'visualizador' END,
    COALESCE(NEW.raw_user_meta_data->>'status', 'pendente'))
  ON CONFLICT (id) DO NOTHING;
  RETURN NEW;
END;
$function$;

CREATE OR REPLACE FUNCTION public.gp_is_admin()
 RETURNS boolean
 LANGUAGE sql
 STABLE SECURITY DEFINER
 SET search_path TO 'public'
AS $function$
  SELECT EXISTS (
    SELECT 1 FROM public.perfis p
    WHERE p.id = auth.uid() AND p.status = 'ativo' AND p.cargo IN ('dev','admin')
  );
$function$;
```
